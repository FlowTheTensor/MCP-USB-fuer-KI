LVL 2 · Station 1 · Grundlagen

Host, Client, Server

HostDie Anwendung, in der die KI arbeitet, z. B. ein Chat-Programm wie Claude Desktop oder ein Code-Editor. Der Host verwaltet die Verbindungen und entscheidet, was das LLM zu sehen bekommt und was es darf.
Nicht verwechseln: Der Host ist ein Programm. Arbeitet das LLM darin selbstständig in einer Schleife, nennt man es einen Agenten (siehe LVL 4 · Agent oder Host?).
ClientEin Baustein im Host. Jeder Client hält genau eine Verbindung zu genau einem Server (1:1). Bei drei Servern hat der Host also drei Clients.
ServerEin eigenständiges Programm, das Fähigkeiten anbietet: Werkzeuge, Daten oder Vorlagen. Er „übersetzt“ zwischen MCP und dem eigentlichen System (Datenbank, Dateien, Web-API …).

Wichtig: Das LLM selbst spricht kein MCP. Es entscheidet nur, welches Werkzeug benutzt werden soll. Die eigentlichen MCP-Nachrichten verschickt der Client im Host. Mehr dazu in LVL 4.

LVL 2 · Station 2 · Vergleich

Das Kabel: Transport

🔌 stdio (lokal)

  • Der Host startet den Server als eigenes Programm auf demselben Rechner.
  • Nachrichten laufen über stdin (Host → Server) und stdout (Server → Host), eine JSON-Nachricht pro Zeile.
  • Auf stdout darf nur MCP stehen. Log-Ausgaben gehören nach stderr.
  • Ideal für Dateien, lokale Datenbanken und Tools auf dem eigenen PC.

📡 Streamable HTTP (remote)

  • Der Server läuft eigenständig, oft im Internet, und kann viele Clients bedienen.
  • Der Client schickt Nachrichten per HTTP POST an einen Endpunkt.
  • Der Server kann Antworten auch als Datenstrom (Server-Sent Events) zurückschicken.
  • Anmeldung z. B. über OAuth. Ideal für Online-Dienste.

So wird im Projekt SQLite-per-MCP der Server in Claude Desktop eingetragen. command und args sagen dem Host, welches Programm er starten soll. Das ist also stdio:

{
  "mcpServers": {
    "sqlite-schule": {
      "command": "C:\\SQLite-per-MCP\\venv\\Scripts\\python.exe",
      "args": ["C:\\SQLite-per-MCP\\src\\index.py"]
    }
  }
}
LVL 2 · Station 3 · Ablauf

Der Handshake

Wie ein USB-Gerät beim Einstecken muss sich ein MCP-Server erst vorstellen, bevor gearbeitet wird. Dabei einigen sich beide auf eine Protokollversion und tauschen ihre Capabilities (Fähigkeiten) aus.

  1. Client → Server initialize (Request): „Hallo, ich spreche Version X und kann Folgendes …“ 
    {
  "jsonrpc": "2.0",
  "id": 1,
  "method": "initialize",
  "params": {
    "protocolVersion": "2025-06-18",
    "capabilities": { "sampling": {} },
    "clientInfo": { "name": "Schul-Host", "version": "1.0.0" }
  }
}
  2. Server → Client Antwort: „Verstanden, ich biete Tools an.“ 
    {
  "jsonrpc": "2.0",
  "id": 1,
  "result": {
    "protocolVersion": "2025-06-18",
    "capabilities": { "tools": { "listChanged": true } },
    "serverInfo": { "name": "SQLite Schul-Datenbank", "version": "1.0.0" }
  }
}
  3. Client → Server notifications/initialized (Notification): „Alles klar, los geht's.“ 
    { "jsonrpc": "2.0", "method": "notifications/initialized" }
  4. Betrieb Jetzt laufen normale Anfragen: tools/list, tools/call … Mit ping kann jede Seite prüfen, ob die andere noch da ist.
  5. Ende Die Verbindung wird geschlossen: bei stdio endet der Prozess, bei HTTP die Sitzung.

Die Protokollversion ist ein Datum (z. B. 2025-06-18). Die jeweils aktuelle Version steht in der Spezifikation. Durch die Capabilities weiß jede Seite, was die andere kann. Ein Server ohne tools-Capability bekommt also gar nicht erst tools/list.
